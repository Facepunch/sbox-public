# s&box projects

## Layout

| Path | What it is |
|---|---|
| `*.sbproj` | The project file: title, ident, type, startup scene, package references, settings. This is what `--project` and `--list` refer to. |
| `Code/` | Runtime C# (components, game logic, Razor UI). Compiled and hotloaded by the editor. |
| `Editor/` | Editor-only C# — inspectors, tools, widgets, and project MCP tools. |
| `Assets/` | Scenes (`.scene`), prefabs (`.prefab`), materials, models, sounds, maps (`.vmap`) and other resources. |
| `ProjectSettings/` | Project configuration (input, collision, etc). |
| `Libraries/` | Library packages added to the project. |
| `Localization/` | Translation tables. |
| `.sbox/` | Local generated data. Not source; ignored by version control. |
| `*.slnx`, `*.csproj` | Generated by the editor for IDEs. **Don't hand-edit**; edit source and `.sbproj` settings. |

Asset paths in tools are relative to the assets root (`models/chair.vmdl`, `scenes/main.scene`).

## APIs

s&box is its own engine with a scene system of `GameObject`s and `Component`s, Razor UI and
Source-style coordinates. It is **not** Unity or Godot, and similarly named APIs differ. Before
using an API:

1. Look for existing usage in the project's `Code/`.
2. Check the installed XML docs in `<engine>/bin/managed/` — `Sandbox.Engine.xml` for game code,
   `Sandbox.Tools.xml` for editor code.
3. Ask the editor: `get_component_type` documents any component's properties, and a quick
   `run_csharp` can confirm a member exists and behaves as expected.

## Edit → compile → verify

1. Save a `.cs` / `.razor` file. The editor notices, compiles and hotloads.
2. Poll `editor_status` until `IsCompiling` is false.
3. Check `LastCompileSucceeded`. On failure, `compile_status` lists every error and warning with
   file and line; `read_console` has the full log.
4. Fix and repeat. Don't move on with a broken build — the editor keeps running the last good code,
   so behaviour you observe won't reflect your edit.
5. Validate behaviour in the editor. Use `play_start` when the change only shows at runtime, then
   `read_console`, screenshots and `run_csharp` against `Game.ActiveScene` to check it. `play_stop`
   when done — runtime changes are discarded.

Keep the editor window visible while validating.

## Scenes and prefabs

- Prefer `scene` tools over editing `.scene` / `.prefab` JSON by hand. They validate, keep
  references intact and are undoable.
- `asset_read` / `asset_write` handle raw JSON for GameResource assets when no dedicated tool exists.
- Scene edits live in the editor until saved. Check `SceneHasUnsavedChanges` and `save_scene` when
  the user expects changes on disk; don't save scenes the user didn't ask you to touch.

## Project Settings > AI

Stored in the `.sbproj` and shared with collaborators.

- **Enable MCP Communication** (`EnableMcpCommunication`, default on) — lets local MCP clients
  connect to this project's editor. Saving it off disconnects clients. Games still need `-mcp`.
